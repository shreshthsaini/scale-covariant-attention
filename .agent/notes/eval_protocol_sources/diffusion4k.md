## 1. Evaluation split definition (the key question)

From the paper:

- "For the evaluation set, Aesthetic-Eval, we select image-text pairs from the LAION-Aesthetics V2 6.5+ dataset, following the criterion of a short image side greater than 2048." ... "the Aesthetic-4K evaluation set consists of 2,781 high-quality images with a median height of 2983 and median width of 3613." ... "Within the evaluation set, 195 images have a short side greater than 4096, which we refer to as Aesthetic-Eval@4096." (P, Section 3.1, PDF p.4). X Section 3.2 repeats this.
- The full 2,781-image set is called Aesthetic-Eval@2048 in the tables (P Tables 3, 4, 9).
- Eval images are not sampled from the internet-collected training images, "to mitigate the risk of overfitting" (P Section 3.1, p.4).
- Table 9 (P supp Section 8, PDF p.12) gives statistics: Aesthetic-Eval@2048 median 2983 x 3613 (h x w), mean 3143 x 3746; Aesthetic-Eval@4096 median 4912 x 6449, mean 5269 x 6420.

From HF (revision 8c5d5cb):

- `eval/size_2048/`: 2,781 image files (2195 .jpg, 222 .jpeg, 42 .JPG, 322 .png) plus metadata.jsonl with 2,781 rows of {"file_name", "text"}.
- `eval/size_4096/`: 195 image files (140 .jpg, 21 .jpeg, 34 .png) plus metadata.jsonl with 195 rows.
- All 195 size_4096 files also exist in size_2048 under the same name, with byte-identical content (same LFS sha256) and identical caption text. Aesthetic-Eval@4096 is therefore a strict subset of Aesthetic-Eval@2048.
- `train/`: 12,015 images in 13 folders plus metadata.jsonl, matching the paper's 12,015 (P Section 3.1).

Duplicates. Neither P, X, the HF card, nor the G README mentions duplicates. I checked the LFS sha256 values from the HF API:

- size_4096: 195 files hold only **168 distinct byte contents**. There are 15 duplicate groups (9 pairs, 2 triples, 3 quadruples, 1 group of 6), so 27 files are redundant copies. Every copy has a different caption (195 distinct captions; 0 of the 15 groups share a caption), so the duplicates look like separate LAION rows that point to the same picture, each captioned separately.
- size_2048: 2,781 files hold only **2,462 distinct byte contents**. There are 221 duplicate groups (sizes: 166 x2, 31 x3, 15 x4, 5 x5, 1 x6, 3 x8), so 319 files are redundant copies.
- Local cross-check: the HF cache snapshot used by our pipeline (/scratch/09032/saini_2/tmp/hf/hub/datasets--zhang0jhon--Aesthetic-4K/snapshots/8c5d5cb.../eval/size_4096/images) has 195 files that resolve to 168 distinct blobs, which matches the internal audit. Our aesthetic4k_eval.jsonl and aesthetic4k_refs.jsonl each have 195 rows, 195 distinct ids, 195 distinct prompts and 195 distinct paths, all at dataset_revision 8c5d5cb.
- Header-only read of those 195 local images: the minimum short side is exactly 4096 (188 are strictly greater than 4096 and 7 are equal to it, while the paper says "greater than 4096"). Median is 4912 x 6449 and mean 5269 x 6421, which matches Table 9 (5269 x 6420 after rounding). So the paper's statistics were computed on the 195 files including duplicates. This is the same split the paper used.

Captions. The paper says captions are "generated by GPT-4o" (P abstract, Section 3.1, Fig. 3 caption, which shows evaluation-set samples). The GPT-4o captioning prompt (P supp Table 11, PDF p.17) is: "Directly describe with brevity and as brief as possible the scene or characters without any introductory phrase like 'This image shows', 'In the scene', 'This image depicts' or similar phrases. Just start describing the scene please." Table 6 compares "original captions from LAION-5B" against GPT-4o captions on Aesthetic-Eval@4096. The original LAION captions are not in the HF metadata, which holds only the GPT-4o style `text`. The "meticulously filtered out low-quality images through manual inspection, excluding those with motion blur, focus issues, and mismatched text prompts" sentence sits in the paragraph that describes Aesthetic-Train (P supp Section 8, p.12). The HF card repeats it without saying which split it covers. Nothing in P says the eval split was manually filtered or deduplicated.

## 2. Base models and checkpoints

- SD3-2B and Flux-12B (P Section 4, p.5). "we use the open-source Flux.1-dev version, which is trained using guidance distillation, and adopt the default guidance scale of 3.5 for WLF" (P supp Section 9, PDF p.15). The G README points to black-forest-labs/FLUX.1-dev and stabilityai/stable-diffusion-3-medium-diffusers.
- All evaluated models use the "partitioned VAE" with F = 16 (P Section 3.2): a dilated first encoder convolution and a partitioned last decoder convolution. In G, `pipeline_flux_4k_wavelet.py` sets `vae_scale_factor = 32`, so 4096 x 4096 means a 256 x 256 latent, which is 128 x 128 = 16,384 tokens, and 2048 x 2048 means 4,096 tokens. "Flux-F16@N" = pretrained FLUX.1-dev with the F16 partitioned VAE and no fine-tuning. "-WLF" = fine-tuned with wavelet loss. Released checkpoint: zhang0jhon/flux_wavelet (later flux_wavelet_v2_sc).
- No training-free high-resolution baselines (HiFlow, I-Max, DemoFusion and others) appear in any table of P. The supplementary has qualitative comparisons only, with PixArt-Sigma and Sana, using images "sourced directly from their official websites" (P supp Section 7, p.11). X Table 5 adds quantitative PixArt-Sigma@2048 and Sana@2048 rows.

## 3. Prompt sets, counts, seeds

- Aesthetic-Eval@2048 (FID, CLIPScore, Aesthetics, GLCM, compression): the paper never states the prompt count used for Tables 3-4. The code default is the full split: `--json_file ./Aesthetic-4K/eval/size_2048/metadata.jsonl` (G generate_and_eval_fid.py l.142), and the script loops over every line, so 2,781 prompts with no subsetting.
- Aesthetic-Eval@4096 (Tables 6-8): the 195 prompts (G l.142 shows the size_4096 metadata path as the commented alternative).
- Images per prompt: 1. Seed: `torch.Generator("cpu").manual_seed(args.seed)` with default seed 0, so the same seed for every prompt (G l.130, l.201). The paper does not state seeds.
- Human preference study: 112 prompts "sampled from Sora, PixArt, SD3, etc.", 10 participants, Flux with vs. without WLF (P supp Section 9, p.17). These are not Aesthetic-4K prompts. P does not state the GPT-4o preference prompt count. X (Section 6.2) puts the "112 text prompts sampled from Sora, PixArt, SD3, etc." sentence right after its GPT-4o description, which implies both studies used the same 112 prompts.
- Metric-validation study: five participants rated extracted patches 1-10 for SRCC/PLCC (P supp Section 9, p.17; Table 1).

## 4. Resolutions

- FID / CLIPScore / Aesthetics / GLCM / compression: 2048 x 2048 on Aesthetic-Eval@2048 (Tables 3, 4).
- CLIPScore / Aesthetics: 4096 x 4096 on Aesthetic-Eval@4096 (Tables 6, 7). GLCM / compression at 4096 for SD3 only (Table 8).
- **No FID is reported at 4096 x 4096 anywhere in P or X.**
- The G README "Tips" recommend 4096x3072 or 3072x4096 at guidance 5 or 5.5 for 4K generation.

## 5. Sampler settings

- P supp Section 9 "Details for Evaluation" (PDF p.15-17): "images are generated using a guidance scale of 7.0, and flow-matching sampling introduced in SD3, with 28 sampling steps for SD3-2B and 50 sampling steps for Flux-12B." P p.8: "discretizing the ordinary differential equation (ODE) process using an Euler solver." X Section 6.1 restates this for "the established Aesthetic-Eval@2048 set".
- For FLUX.1-dev, "guidance scale 7.0" is the distilled-guidance embedding value. G defaults: `--guidance_scale 7.0` with comment "# 5.0" and help text "the FLUX.1 dev variant is a guidance distilled model, default 3.5 for original FLUX.1 dev"; `--num_inference_steps 50`; `max_sequence_length 512` for Flux (77 for SD3); BF16 pipeline (G l.100-130, l.157-201).
- Scheduler: the diffusers FluxPipeline dynamic shift, `sigmas = np.linspace(1.0, 1/N, N)`, `mu = calculate_shift(image_seq_len, base_image_seq_len, max_image_seq_len, base_shift, max_shift)` from the scheduler config (G pipeline_flux_4k_wavelet.py l.57-66, l.657-672). This is a single stage with no cascade.
- Precision: BF16 (P Table 5 caption; G l.157).

## 6. Metrics and implementation

Paper text: "The FID, Aesthetics and CLIPScore are computed using resized images at a fixed low resolution" (P supp Section 9, PDF p.17). The paper does not state the resolution. X Section 6.1: FID compares features "extracted by Inception v3 at a resolution of 299 x 299"; "The Aesthetics score is predicted using a simple linear model on top of CLIP ViT-L/14".

Code (G generate_and_eval_fid.py, pins from requirements.txt: torchmetrics 1.5.1, torch-fidelity 0.3.0, torch 2.4.0, torchvision 0.19.0, diffusers 0.30.3, transformers 4.45.1, scikit-image 0.24.0):

- **FID**: `torchmetrics.image.fid.FrechetInceptionDistance(normalize=False)`. This defaults to 2048-d pool features and the torch-fidelity "inception-v3-compat" network, which internally resizes every input to 299 x 299 (torchmetrics docstring). Real (reference) images are **the eval split's own images**, one per prompt, so 2,781 at @2048 and 195 at @4096. Both real and generated images go through `fid_preprocess`: torchvision `F.resize(image, size)` (short side to `size`, i.e. 2048) then `F.center_crop(image, (size, size))` (G l.79-84, l.205-206). The result is one whole-image FID per run, with N_gen = N_real = split size. There is **no patch/crop FID, no KID, no IS**. Duplicate reference images are counted as many times as they appear.
- **CLIPScore**: `torchmetrics.functional.multimodal.clip_score` with `openai/clip-vit-base-patch16`, applied to the full generated image and averaged over prompts (G l.165-168, l.209). The CLIP processor's resize to 224 is library behavior and is not stated in the paper.
- **Aesthetics**: OpenAI `clip` ViT-L/14 preprocess plus the LAION improved-aesthetic-predictor MLP `sac+logos+ava1-l14-linearMSE.pth` on L2-normalized embeddings, averaged (G l.29-53, l.174-178, l.212-216).
- Generated images are saved as JPEG with quality=95 (G l.222). FID, CLIP and Aesthetics use the in-memory image. GLCM and compression use the saved JPEGs.
- **GLCM Score** (P Section 3.1 p.5; G eval.py): the paper formula is s = -(1/P) sum_p H(g_p) (a leading minus sign is printed; X eq. 11 is the same), with 64 gray levels, distances [1,2,3,4], angles [0,45,90,135] degrees, and 64-pixel patches. The code converts with `cv2.cvtColor(BGR2GRAY)`, quantizes with `i//4` to 64 levels, tiles non-overlapping 64x64 patches over `size x size` (1024 patches at 2048, 4096 at 4096), computes `graycomatrix(..., levels=64, normed=True)`, scores each patch as `skimage.measure.shannon_entropy(glcm)` with **no minus sign**, and averages over patches and then over images. skimage's shannon_entropy is the base-2 entropy of the histogram of unique values in the array (checked in an installed skimage copy). That is not the textbook GLCM entropy -sum p log p. The paper does not reconcile the minus sign with the reported positive, higher-is-better values.
- **Compression Ratio**: (size x size x 3 bytes x N) / (sum of JPEG q95 file sizes), a ratio of totals over all images in the folder (G eval.py l.79-107). Lower is better. The paper says "ratio of the original image size in memory to the compressed image size using the JPEG algorithm at a quality of 95" (P p.5).
- **Reference-free IQA**: MUSIQ and MANIQA appear only in the metric-correlation Table 1 and are not used for model comparison. The paper does not state their implementation or input resolution.
- **Preference**: pairwise human (10 raters, 112 prompts) and GPT-4o (prompt in P supp Table 11) win rates, Flux-F16@4096 vs Flux-F16-WLF@4096 (P Section 4.2, Fig. 6).
- Not used: ImageReward, HPS, PickScore, CLIP-IQA, patch FID, KID, IS.

## 7. Latency hardware

"tested on one A100 GPU with BF16 Precision" at 4096 x 4096 (P Table 5). Fine-tuning used 2 A800-80G (SD3) and 8 A100-80G (Flux) (P Section 4.1, p.6).

## 9. NOT STATED / UNVERIFIED

- NOT STATED in the paper: the "fixed low resolution" used for FID, CLIP and Aesthetics. The code shows a resize plus center crop to `size`, then torchmetrics' internal 299, CLIP's 224, and CLIP ViT-L/14's 224. Also not stated: seeds, images per prompt (the code gives 1 at seed 0), any FID at 4096, the GPT-4o preference prompt count, the MUSIQ/MANIQA implementation, and the presence of duplicates in the eval split.
- The code is a 2025-11-24 snapshot. I cannot verify that the paper numbers were produced with exactly this script (UNVERIFIED).
